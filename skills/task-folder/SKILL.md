# 태스크 폴더 (3층 구조) 만들기

대상: `$ARGUMENTS`

> **왜 나누는가**: 태스크 문서 하나가 수천 줄로 커지면 세션마다 통째로 읽거나 "전문 Read 금지"를 따로 달아야 한다. 세션 시작마다 필요한 것은 **짧은 현황**이고, 결정 근거·검증 로그는 **필요할 때 grep**하면 된다.
> **적용 범위**: 새로 만드는 문서만. 기존 평면 문서는 그대로 이어 쓴다 — 작업 도중에 쪼개면 다른 세션과 충돌하고 절 번호 참조가 깨진다.
> **내용 골격**은 `/plan`(Goal·AC·Steps·Verification·Risk)을 따른다. 이 스킬은 **어디에 어떻게 나눠 담는가**만 정한다.
> 프로젝트에 태스크 문서 규약이 있으면 그쪽을 따른다.

## 1. 위치와 구조

- 태스크 디렉토리: 프로젝트 `CLAUDE.md`에 지정이 있으면 그곳, 없으면 기존 태스크 문서가 있는 곳(`docs/tasks/`, `tasks/` 순), 그것도 없으면 `docs/tasks/`.

```
<태스크 디렉토리>/<작업명>/
├── STATUS.md       # 매 세션 가장 먼저 읽는 현황 — 150줄 상한
├── DECISIONS.md    # append-only 결정 로그 — D-001부터
├── WORKLOG.md      # append-only 상세 기록 — 조사·리뷰·검증 출력·교훈
└── handoff/        # 세션 인계 프롬프트 (/session-handoff) — YYYY-MM-DD-<주제>.md
```

- 외부로 나가는 문서(연동 가이드·질의서)는 같은 폴더에 별도 파일로 둔다.

## 2. STATUS.md 템플릿

```markdown
# <작업 제목>

- **상태**: 🟡 진행 중 | 🟢 완료 | 🔴 차단 — <한 줄 요지> (YYYY-MM-DD)
- **브랜치**: `<branch>` · **최종수정**: YYYY-MM-DD
- **관련 문서**: DECISIONS.md · WORKLOG.md

## 목표 & 수용 기준
- 무엇을:
- 끝났다는 기준: (검증 가능한 문장으로)
- 비목표:

## 지금 어디까지 (다음 세션이 여기서 이어간다)
- 완료: (1줄씩, 상세는 WORKLOG의 날짜 절)
- **다음 할 일**: (1~3개, 첫 줄이 바로 착수할 것)

## 진행 체크리스트
- [ ] S1 — (가장 작은 검증 가능 단위)

## 미해결 질문 · 차단
| # | 질문 | 누구에게 | 권장 디폴트 | 상태 |
|---|---|---|---|---|

## 결정 요약 (본문은 DECISIONS.md)
- D-001 <한 줄>

## 검증 명령 (DoD)
- (이 작업에서 실제로 돌릴 명령)

## 위험 & 롤백
-
```

## 3. DECISIONS.md 템플릿

```markdown
# <작업 제목> — 결정 로그

> 새 결정은 맨 아래에 추가한다. 기존 항목은 고치지 않고, 뒤집힐 때는 새 항목에 `supersedes D-00N`을 쓴다.

## D-001 — <결정 한 줄> (YYYY-MM-DD)
- **맥락**: 왜 결정이 필요했나
- **결정**:
- **근거**: 파일:라인 · 원문 · 실측 명령과 결과
- **버린 대안**:
- **영향**: 바뀌는 코드·문서·소비자
```

## 4. WORKLOG.md

- 날짜 절(`## YYYY-MM-DD — <주제>`)을 **맨 아래에 추가**한다. 조사 결과표, 리뷰 지적과 조치, 검증 출력 요약, 교훈을 둔다.
- 커져도 된다 — 대신 통째로 읽지 않는다.

## 5. 운영

- 유지 규칙(150줄 상한 · append-only · 부분 읽기 · 중복 금지)은 `rules/task-folder.md`가 정본이다 — 이 폴더의 파일을 열면 자동 로드된다.
- 참조는 `D-00N`·`WORKLOG YYYY-MM-DD 절`처럼 **안정적인 ID/날짜**로 한다 (절 번호는 삽입 시 밀린다).

## 6. 만든 뒤 확인

- [ ] 세 파일 모두 생성, STATUS 150줄 이하
- [ ] STATUS "다음 할 일"이 비어 있지 않다
- [ ] 수용 기준이 검증 가능한 문장이다
